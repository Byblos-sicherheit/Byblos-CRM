# Output Contracts

Adapt depth to the task. Do not force every section into simple answers.

## Explanation or teaching

- Direct answer
- Mental model
- Minimal example
- Common failure or misconception
- Verification or exercise when useful

## Requirements analysis

- Objective
- Users and use cases
- Functional requirements
- Non-functional requirements
- Inputs, outputs, data, and integrations
- Failure cases
- Constraints and unknowns
- Acceptance criteria
- MVP boundary

## Architecture or technology decision

- Context and constraints
- Options considered
- Decision
- Component/data-flow description
- Security and failure model
- Trade-offs
- Migration/deployment approach
- Revisit trigger

## Implementation

- Goal
- Changes made
- Important design decisions
- Files changed
- Verification commands and observed results
- Remaining risks/manual steps

## Code review

Start with findings, ordered by severity:

### [Severity] Finding title
- Evidence: file and line/range
- Problem
- Consequence
- Remediation
- Test needed

Then include:
- Assumptions or questions
- Brief change summary
- Verification performed

Do not return “looks good” unless the relevant code and checks were actually examined.

## Debugging

- Reproduction
- Evidence
- Root cause
- Fix
- Regression test
- Verification
- Remaining uncertainty

## Security audit

- Scope and threat assumptions
- Findings by severity
- Exploitability and impact
- Evidence
- Remediation
- Verification plan
- Residual risk

Do not claim full security or compliance certification from a limited review.

## Complete project delivery

Include:
- Project tree or package contents
- Prerequisites
- Configuration and secret-handling instructions
- Install/build/run/test commands
- Deployment or packaging instructions
- Architecture summary
- Known limitations
- Verification status

A scaffold must be labeled as a scaffold. A project is “runnable” only if the relevant build/run path was verified in the available environment.
